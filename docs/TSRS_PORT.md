# Rust port on tsrs: the plan

This document records the agreed plan for porting effect-tsgo's Effect Go code to Rust on top of
[tsrs](https://github.com/oxc-project/tsrs), the Rust port of typescript-go. How to port a declaration is in
[`PORTING.md`](PORTING.md); how shim APIs map to tsrs is in [`TSRS_API.md`](TSRS_API.md); accepted differences
are in [`DIVERGENCES.md`](DIVERGENCES.md).

## Goal

A Rust build of `@effect/tsgo` with the same observable behavior as the Go build: the Effect diagnostics, quick
fixes, refactors, completions, hover, inlay hints, document symbols and CLI diagnostics mode. The Go build stays the
default; users opt in to the Rust one. The Go code is the specification and keeps evolving; the Rust port follows it
in the same pull request.

## Decisions

| Topic | Decision |
| ----- | -------- |
| What is ported | The Effect Go code: `etscore`, `etscheckerhooks`, `etsdiagnostics`, `etsexecutehooks`, `etslshooks`, `etsgoapi`, and `internal/...` (rules, fixables, refactors, completions, type parser, layer graph, rule runner, ...). About 58k lines and 139 rules. `porting/scope.toml` is the authority |
| Parity | Full: diagnostics, quick fixes, refactors, completions, hover, inlay hints, document symbols, the CLI diagnostics mode, and exit-code filtering |
| Not ported | `etsoxlintrunner` and everything oxlint/tsgolint: the oxlint integration stays Go-only. Go tooling (`_tools/`). Generated Go code (it is regenerated for Rust instead) |
| Layout | 1:1 mirror: one crate per Go package under `crates/`, one `.rs` per `.go`, declarations in Go order. Crate name: `ets_` + package path minus `internal/`, non-alphanumerics -> `_` (`internal/rules` -> `ets_rules`, `etscore` -> `ets_etscore`). `pnpm exec repoctl tsrs port-crate <pkg>` prints it |
| TypeScript side | tsrs, as a new component in `_packages/tsgo/upstream.json`, checked out as a repoctl-managed submodule like `typescript/`. It is checked out only by `pnpm exec repoctl submodules setup --component tsrs` (the TypeScript commit that tsrs release ports plus tsrs, both patched, so Go and Rust both build in that checkout and run the same TypeScript; see "The TypeScript tsrs ports" below); `pnpm setup-repo` (the default `typescript` component) drops it again, like an oxlint checkout. Changes to tsrs are in-place patches in `_patches/tsrs/NNN-*.patch`, applied by that setup. Cargo `[patch]` points every tsrs crate at the submodule |
| Patch numbering | A tsrs patch that ports a `_patches/typescript` patch takes that patch's number and name (`023-checker-effect-links.patch`). A tsrs-only patch (no Go counterpart, e.g. a visibility change the Go shim gets via linkname) takes a number from 100 up |
| Shim rule | Effect crates never depend on `tsrs_*` crates directly. They depend only on the generated `ets_shim` crate, which re-exports tsrs per Go shim package (`ets_shim::checker`, `ets_shim::ast`, ...), mirroring the Go rule that Effect code imports only `github.com/microsoft/TypeScript/tsc/shim/...`. `ets_shim` is generated by the tsrs setup (committed; the default setup leaves it alone) and never edited by hand |
| Baselines | Shared: `testdata/baselines/reference` is the single source of truth for both builds. A Rust baseline runner (`ets_effecttest`, the port of `internal/effecttest`) produces the same files and diffs them against the reference |
| Baseline failures | Any baseline mismatch fails the Rust runner (and CI), as in Go; the actual output is written to the ignored `testdata/baselines/local-rs/`. During the initial port a shrink-only allowlist (`porting/expected-failures.tsv`) tolerated known differences; it was emptied and deleted when Phase 4 ended |
| TypeScript version | tsrs pins its own TypeScript snapshot. The Rust build is compared against a Go build at tsrs's TypeScript version (a `typescript` entry in `upstream.json` at that commit, which the `tsrs` component names as its dependency), so a difference is a port bug unless the Go build at that version shows it too |
| Shipping | A `tsrs` patcher component, like `typescript` and `oxlint`. Users install tsrs themselves (`npm i tsrs`) and opt in with `effect-tsgo patch --tsrs`, which swaps the binary of the installed `@tsrs/<target>` package for our Effect-patched build of the same tsrs version, shipped in the `@effect/tsgo` platform packages (`artifacts/tsrs/<tsrs version>/tsrs`). TypeScript patching is unchanged: the Go build stays the default for `typescript` |
| Parity policy | Every pull request that changes ported Go code updates the Rust port in the same pull request; CI (`repoctl tsrs port-check` in the Validate tsrs workflow; locally `pnpm check`) fails otherwise. See below |
| Extras | `repoctl perf compare` can compare the Go and Rust builds. The upstream-bump automation (`update-upstreams.yml`) also bumps tsrs and rebases `_patches/tsrs` |

## Architecture

```
_packages/tsgo/upstream.json      components: typescript, oxlint, oxlint-tsgolint, tsrs (new)
tsrs/                             submodule at the tsrs component's gitHead (repoctl-managed, reset on setup)
_patches/tsrs/NNN-*.patch         in-place patches applied to tsrs/ by `repoctl submodules setup --component tsrs`
Cargo.toml                        workspace: members = crates/*; [patch] -> tsrs/crates/<crate>
crates/ets_shim/                  generated: re-exports tsrs per shim package (+ accessors exposed by patches)
crates/ets_<pkg>/                 one crate per Go package, 1:1 with the Go files
crates/<binary>/                  Rust-only: the executable; registers the hook crates and runs tsrs's CLI/LSP
porting/                          scope.toml, manifest.tsv, skipped.tsv, ported.tsv
testdata/baselines/reference/     shared baselines (Go and Rust)
```

- Dependency direction: `ets_<pkg>` -> `ets_shim` -> `tsrs_*`. Crate-to-crate edges between `ets_*` crates are
  exactly Go's import edges.
- Hook registration: Go registers the checker, LS and execute hooks from `init()` functions, imported by the patched
  `cmd/tsc/main.go` (`_patches/typescript/001-cmd-tsgo-main.patch`). Rust has no `init()`: each hook crate has a
  `pub fn init()` (run once, in Go's order), and the binary calls them before handing over to tsrs's CLI. The tsrs
  side of the hook points (callback registries in the checker, LS and execute paths) are ports of the matching
  `_patches/typescript` patches.
- Go stdlib stand-ins: where Go's standard library behavior is observable (`fmt` verbs, `sort` tie order,
  `strings.ToLower`, `regexp`, `encoding/json`), see `PORTING.md`, "Go runtime equivalents".

## Phases

Each phase ends when its exit criteria hold on `main`.

### Phase 0: porting tooling, docs, skills

- `repoctl tsrs port-*` (manifest, status, todo, check, fix-lines, ack, diff, crate, deps, ready), the check wired into `pnpm check`.
- `porting/scope.toml`, an initial `porting/manifest.tsv`, empty `skipped.tsv` / `ported.tsv`.
- This document, `PORTING.md`, `TSRS_API.md`, `DIVERGENCES.md`, the skills in `.claude/skills/`, a short "Rust
  port" section in `AGENTS.md`.

Exit: `pnpm exec repoctl tsrs port-manifest` is stable and `repoctl tsrs port-check` passes on a tree with no Rust code.

### Phase 1: foundations

- `tsrs` component in `upstream.json`, the submodule, `repoctl submodules setup` support for it.
- First `_patches/tsrs` patches (at minimum what `ets_shim` and the first crates need: the hook registries and the
  visibility changes for the shim accessors they use).
- `ets_shim` generation in the tsrs setup; the Cargo workspace (toolchain pinned to tsrs's, workspace lints,
  `[patch]`); the first `ets_*` crates compiling against `ets_shim`.

Exit: `cargo build` and `cargo clippy --all-targets` pass from a fresh clone after `pnpm exec repoctl submodules setup --component tsrs`; no `ets_*`
crate depends on a `tsrs_*` crate; `repoctl tsrs port-check` passes with their markers acked.

### Phase 2: Rust baseline runner, allowlist, repoctl/CI

- `ets_effecttest` (port of `internal/effecttest`): diagnostics, quick fix, refactor, completion, hover, inlay hint
  and document symbol baselines, written where the Go runner writes them and diffed against the reference.
- `porting/expected-failures.tsv` with the shrink-only check (removed at the end of Phase 4); the Rust steps
  (`cargo check`, `cargo fmt --check`, `cargo clippy`, `cargo test`) as `repoctl tsrs check|lint|test`, separate
  from the Go `repoctl check` / `lint` / `test`; CI jobs.
- The Go build at tsrs's TypeScript version available to CI for comparison.

Exit: CI runs the Rust lane on every pull request; every baseline is either matching or allowlisted.

CI layout: the Rust lane is its own workflow. `repoctl check`, `lint` and `test` run no Rust, and `validate.yml`
(Validate, the TypeScript matrix) uses the default setup, which has no tsrs checkout and no Rust toolchain, and runs
nothing of the Rust port. `validate-tsrs.yml` (Validate tsrs, one ubuntu job) runs the setup action with
`component: tsrs` (the latest tsrs next to the TypeScript it ports, both patched, the Go shims and
`crates/ets_shim` regenerated) and `rust: true` (toolchain, CMake, rust-cache), then first
`repoctl tsrs port-check --summary` (also part of `repoctl check`; Node and Go only, so a parity failure shows before
the Rust build; it posts the progress table), then `repoctl tsrs lint`
(`cargo fmt --check`, Clippy with `-D warnings`), `repoctl tsrs check` (`cargo check`) and `repoctl tsrs test`
(`cargo test --workspace`, including the baseline runner, then the dev-profile tsrs binary and its `--version`). It
does no Go build: the Rust tests read only committed files and the Effect fixtures that `repoctl submodules setup`
prepares. The `repoctl tsrs` cargo commands fail without a tsrs checkout.

### Phase 3: core

`etscore`, `internal/typeparser`, the rule framework (`internal/rule`, `internal/fixable`,
`internal/refactor`, `internal/completion`, `internal/directives`, `internal/rulerunner`), `etscheckerhooks`, plus
the tsrs patches they need. Ported by hand or by a single agent per package and reviewed carefully: everything later
builds on them.

Exit: these packages are fully ported (`repoctl tsrs port-status <pkg>` at 100% or skipped with reasons), their ported Go
tests pass, and a first set of rule baselines matches.

### Phase 4: agent fan-out (done)

Rules, fixables, refactors, completions, the LS hooks (`etslshooks`), `etsdiagnostics`, `etsexecutehooks`,
`layergraph`, `schemagen`, ... in batches dispatched by the `port-next` skill (`port-package` agents in worktrees).
Each batch is gated by `repoctl tsrs port-check` and must shrink `expected-failures.tsv`.

Exit: `repoctl tsrs port-status` shows nothing left to do; `expected-failures.tsv` is empty and deleted; `require_new`
is enabled in `porting/scope.toml`.

Done: every in-scope Go declaration and Go test is ported (`repoctl tsrs port-status`: 100% code, 100% tests), every
shared baseline matches, the allowlist and its machinery are gone, and `require_new = true`. From here on the
steady state is the parity policy below: every change to in-scope Go code updates the Rust port in the same pull
request.

### Phase 5: ship

The `tsrs` patcher component (`effect-tsgo patch --tsrs`), bundling the patched tsrs binary in the platform
packages, the cost of the Effect rules on the Rust engine (`repoctl perf compare --engine tsrs`), automatic tsrs bumps
in the upstream-update workflow.

The component: `effect-tsgo patch --tsrs` (opt-in, like `--oxlint`; `--no-typescript --tsrs` patches tsrs alone)
finds the user's installed `tsrs` package from the working directory, then its platform package `@tsrs/<target>`
(`darwin-arm64`, `linux-x64-gnu`, `linux-x64-musl`, `linux-arm64-gnu`, `linux-arm64-musl`; glibc vs musl as for
Oxlint), and replaces the binary at `<platform package>/tsrs` (the `lib*.d.ts` files next to it are left alone) with
our patched build of that package's version, keeping the original as `tsrs.original` (`effect-tsgo unpatch --tsrs`
restores it). The replacement is resolved like the TypeScript one: by version (`upstream.json` `components.tsrs`),
from `@effect/tsgo-<platform>`, with the hash check that skips an already-patched binary. An unsupported tsrs
version or a musl install is reported as unavailable with the reason (skipped with `--skip-missing`). TypeScript
discovery and replacement are unchanged; `get-exe-path` and `diagnostics` stay TypeScript-only, as for Oxlint. The
setup wizard does not manage tsrs yet; it keeps a `--tsrs` flag when it rewrites the `prepare` script.

Perf: `repoctl perf compare --engine tsrs` measures stock tsrs vs Effect-patched tsrs, the counterpart of the default
stock vs patched tsgo comparison (patched Go vs patched Rust is not a goal). Stock is tsrs's own CLI (`tsrs_cli`) built
from a clean checkout of the pinned tsrs commit under `_tools/.perf-tsrs/<gitHead>` (gitignored; no `_patches/tsrs`,
no Effect crates); patched is `ets_tsrs`. Both use this repository's `[profile.release]` (passed to the stock build as
`cargo --config` overrides), so the difference is our patches and rules; tsrs's npm release binary (PGO/BOLT) is not a
fair baseline. Runs set `TSRS_CHECKER_ASSIGNMENT=go` (`--checker-assignment`; tsrs rejects `--checkerAssignment` with
`-b`). tsrs prints tsgo's `--extendedDiagnostics` table, but "Memory used" is the RSS at the end of each project (the
aggregate sums them) and allocations are not counted, so compare uses the wall time and peak RSS it measures itself
(GNU time, Linux). `--effect-workload` prepares the target as perf CI's pinned Effect workload with all rules:

```sh
repoctl perf compare --engine tsrs --effect-workload --runs 7 --diagnostics-flag=--extendedDiagnostics <dir>
```

`repoctl perf compare --engine tsrs` builds the patched binary from this workspace, so it needs the tsrs setup.
Perf CI (`repoctl perf ci`, the PR matrix) stays tsgo-only: a cell would need two extra fat-LTO Rust builds.

Release build: our binary (tsrs CLI + `_patches/tsrs` + Effect crates) is built by our pipeline, not taken from tsrs's
releases. `repoctl build artifact --component tsrs --version <tsrs version> --target <t>` builds it into
`_packages/tsgo-<t>/artifacts/tsrs/<tsrs version>/tsrs`, using `[profile.release]` copied from tsrs's (fat LTO, one
codegen unit, stripped; keep in sync on tsrs bumps). Platforms: tsrs's own glibc and macOS targets (darwin-arm64,
linux-x64, linux-arm64); tsrs's musl packages are discovered but skipped with "Linux musl is not supported by the
packaged tsrs integration", and hosts tsrs publishes no binary for have nothing to patch. Add targets as tsrs adds
them. PGO/BOLT (tsrs's `pgo-train.sh`/`bolt.sh`, trained on our binary) is not planned until
`repoctl perf compare` shows it's worth the build time.

How it is wired: `tsrs` is a release component like `typescript` and `oxlint`, independent of the TypeScript
versions: the release plan has one `<target>__tsrs__<tsrs version>` job per `components.tsrs` version and tsrs target
(`releasePlan.ts`), built natively on tsrs's runners (`macos-14`, `ubuntu-22.04` for glibc 2.35, `ubuntu-22.04-arm`)
with the Rust workspace toolchain and CMake (`rust: true`, setup-repo). `repoctl submodules setup --component tsrs
--version <v>` checks out tsrs at that version's gitHead (next to the TypeScript it ports, for the codegen).
`packages assemble`, `packages prepare` (executable bits) and `build verify-release` cover every tsrs version on the
tsrs targets and reject an `artifacts/tsrs` directory anywhere else. `repoctl build local` builds the dev-profile tsrs binary
only with a tsrs checkout, cargo and CMake, and otherwise says why it skipped it. The update-upstreams workflow runs the tsrs setup (so a
`_patches/tsrs` patch that no longer applies is reported and `crates/ets_shim` is regenerated), then the default setup
again, so the generated pull request commits no tsrs submodule. `repoctl upstream update` records `tsrs@latest` (tag
`v<crate version>`, TypeScript from its `[workspace.metadata.typescript]`); a patch that no longer applies sets the
`patch_failure` output of `repoctl submodules setup`, which the update-upstreams workflow writes into the pull request
body and the generation check.

Exit: a release ships the patched tsrs binary behind `effect-tsgo patch --tsrs`; perf numbers published; the bump workflow rebases
`_patches/tsrs` or opens a failing PR that says which patch broke.

## Parity policy

- **Same pull request.** A pull request that changes a ported Go declaration must update its Rust port. The
  mechanism: `porting/ported.tsv` stores, per ported declaration, the hash of the Go declaration the Rust was synced
  to. When the Go changes, `repoctl tsrs port-check` (part of `pnpm check`) fails with a hash mismatch until the Rust is
  updated and `repoctl tsrs port-ack` records the new hash. The `port-change` skill does this.
- **Moved, removed or renamed declarations** fail `check` too (unknown or misplaced markers); fix the Rust and run
  `repoctl tsrs port-fix-lines`.
- **New declarations.** The port is complete and `require_new` is enabled in `porting/scope.toml`: a new in-scope Go
  declaration (code or test) must be ported (marker + `repoctl tsrs port-ack`) or listed in `porting/skipped.tsv` with a
  reason in the same pull request; `repoctl tsrs port-check` fails otherwise.
- **Behavior.** Any baseline mismatch fails the Rust runner and CI, exactly as in the Go runner. There is no
  allowlist: a Rust-only difference is fixed in the same pull request (`fix-parity`); an unavoidable tsrs
  difference is recorded in `docs/DIVERGENCES.md` with evidence, never tolerated by the runner.
- `port-ack` is not a way to silence `port-check`: ack only after the Rust matches the new Go.
- **Compiler patches.** A change to `_patches/typescript` is mirrored in the same pull request into every
  `_patches/typescript-<gitHead>` override folder (below) and, where the patch has a tsrs counterpart, into
  `_patches/tsrs`. `repoctl check` fails when an override folder does not hold the same patch file names as
  `_patches/typescript`.

## The TypeScript tsrs ports

A tsrs release ports one TypeScript commit (tsrs 0.18.0: TypeScript `7.1.0-dev.20260929`, `b85298b6`), recorded as
the tsrs component's `typescript` dependency. `repoctl submodules setup --component tsrs` checks out that commit, not
TypeScript next, so the Go build compared with the Rust one runs the same TypeScript. It is a `components.typescript`
entry of its own, kept by `repoctl upstream update` while that tsrs is recorded and switched on a tsrs bump.

Patches and shims are selected by folder naming convention (`_patches/typescript/README.md`, "Per-commit override
folders"): the plain folders target TypeScript next, and a folder suffixed with a TypeScript component's `gitHead`
replaces the plain one as a whole for that commit. `repoctl check` fails on an override folder that names no recorded
TypeScript component ("stale override folder").

- **Patches.** Our `_patches/typescript` stack targets TypeScript next and does not apply to that older commit (the
  `tspath.Path` -> `tspath.PathKey` rename and the generated compiler options landed after it).
  `_patches/typescript-b85298b6a81f772d080b0455de0ca9d744cd6fd6` holds the same patches, file for file, backported to
  that commit with the same behavior and the same exported API (see its README), and is applied instead.
- **Shims.** The Go shims are generated through
  `_tools/gen_shims/providers/typescript-b85298b6a81f772d080b0455de0ca9d744cd6fd6` alone (in place of the
  `typescript` provider overlays), whose `compatibility.go` adapters present the canonical (next) shim API over the
  older compiler, the way the `typescript-go` provider does for 7.0.2.
- **tsrs bump.** When tsrs moves to another TypeScript, both folders turn stale: rename them to the new `gitHead`
  (re-making what no longer applies), or delete them once `_patches/typescript` and the canonical shims apply to it.
- **Release and CI.** It is a TypeScript component like any other: a patched compiler is released for it, the
  Validate matrix tests it (job named after its version) with the shared baselines. The perf matrix skips it: its
  commit has no npm release, so there is no stock compiler to compare against.
  `repoctl upstream update` keeps the entry while the pinned tsrs depends on it and drops it on a tsrs bump that
  moves the TypeScript. `pnpm lint` runs on the next job only, as for every other version.

## Open risks

- **tsrs checker non-determinism** ([tsrs#725](https://github.com/oxc-project/tsrs/issues/725)): tsrs's parallel
  checker assignment can make results depend on scheduling (type ids, union order, which checker checks which
  file). Baseline runs and comparisons use `--checkerAssignment go` (Go's assignment) until fixed. A flaky baseline
  is investigated as non-determinism first, never papered over to make it pass.
- **Binary size**: shipping the patched tsrs binary (one per supported tsrs version) next to the Go binaries grows
  the darwin-arm64, linux-x64 and linux-arm64 platform packages. Options if this is a problem: separate optional
  packages for the tsrs binary, or download on `patch --tsrs`.
- **tsrs API churn**: tsrs is young and its public API moves. `ets_shim` absorbs renames in one generated place;
  tsrs bumps are their own pull requests (`sync-upstream`); patches are kept minimal so they rebase. PRs to tsrs are
  closed, so every change we need lives in `_patches/tsrs` indefinitely.
- **TypeScript version skew**: tsrs's TypeScript snapshot differs from the Go build's default. Differences caused by
  it must be proven (Go at tsrs's version shows them too) and recorded in `DIVERGENCES.md`.
- **Memory model**: tsrs's arena-allocated `'static` AST and types, regions and checker handles differ from Go's GC
  (`TSRS_API.md`). Long-lived LS sessions must free programs the way tsrs's own project system does.
